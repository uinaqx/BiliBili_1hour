### 错误处理 · 00:19:44

请看这道题。read 尝试解析字母 x，失败时通过 map_err 换成格式错误，再跟着一个问号。程序最后会不会返回 Ok 里面的十。还是会返回别的结果。请特别判断，加十这一行有没有机会执行。先思考四秒钟。

```rust
fn read(text: &str) -> Result<u32, &'static str> {
    let n = text.parse::<u32>().map_err(|_| "格式错误")?;
    Ok(n + 10)
}
fn main() {
    println!("{:?}", read("x"));
}
```

### 迭代器 · 00:31:32

这道题把刚才的筛选和加分连在一起。原来是五十、六十、八十，先保留大于等于六十的分数，再给留下的每一个分数加一。请预测最终数组，并判断原来的五十分有没有机会变成五十一出现在结果里。思考四秒钟。

## 答案与解释

### 类型转换 · 00:06:53

第一行输出四十四，第二行输出 true。原因是，as 进行的是这次无符号整数的窄化转换，它没有替我们检查三百能不能完整保留下来。try_from 则会检查能否转换，三百超出八位无符号整数的范围，所以结果是 Err。is_err 对这个结果的判断当然为真。

这道题不要求你背所有整数的位数表，而是要求你先问清楚：我需要的是一种允许改变数值的转换，还是一次必须保留原值的检查。把这个问题问清楚，选择转换方式就有了依据。下面我们把分散的函数组织起来，进入模块。

```rust
fn main() {
    let value: u16 = 300;
    println!("{}", value as u8);
    println!("{}", u8::try_from(value).is_err());
}
```

结果：
```text
44
true
```

### 模块 · 00:13:33

原代码不能编译，因为主函数从模块外访问了私有函数。对于这道题，最直接的修正就是在 passed 前面加 pub，把这个函数作为模块的公开接口。修正以后，八十分满足大于等于六十，程序输出 true。

请留意，use 不能绕过私有规则。就算换一种更短的名字，原本不可访问的函数也不会因此公开。这也是为什么我们要先理解模块路径和可见性，再使用 use 来简化写法。现在代码已经可以分门别类了，下一步学习怎样把操作可能失败这件事表达清楚。

```rust
mod grades {
    pub fn passed(score: u32) -> bool {
        score >= 60
    }
}
fn main() {
    println!("{}", grades::passed(80));
}
```

结果：
```text
true
```

### 错误处理 · 00:20:07

结果是 Err，里面的文字是格式错误。解析字母 x 失败以后，map_err 先把错误换成这段文字，问号接着让 read 提前返回。所以后面的加十不会执行，更不会因为解析失败就把数字当成零。

现在你可以把错误处理读成一个明确的流程：哪些操作可能失败，失败在哪一层处理，哪些情况应该返回给调用者。这个流程想清楚之后，再选择 match、问号或其他辅助方法，代码就不容易写成“看起来处理了，实际上仍然随时崩溃”的样子。接下来，我们学习用测试主动检查这些行为。

```rust
fn read(text: &str) -> Result<u32, &'static str> {
    let n = text.parse::<u32>().map_err(|_| "格式错误")?;
    Ok(n + 10)
}
fn main() {
    println!("{:?}", read("x"));
}
```

结果：
```text
Err("格式错误")
```

### 单元测试 · 00:25:37

它能够编译，但测试会失败。因为 passed 对六十分返回 false，测试却要求这个条件为真。我们检查及格规则以后，应把函数修正为大于等于六十，而不是为了看到通过，就把断言删掉。

修正后，同样的五十九、六十、六十一三个检查都成立，报告显示测试通过。请养成一个小习惯：发现问题以后，尽量留下能重现它的测试，再修正实现。这样以后修改其他部分时，如果旧问题重新出现，这个测试还能提醒我们。

```rust
fn passed(score: u32) -> bool { score >= 60 }
#[test]
fn passing_boundary() {
    assert!(!passed(59));
    assert!(passed(60));
    assert!(passed(61));
```

结果：
```text

```

### 迭代器 · 00:31:58

输出是六十一和八十一。五十分在 filter 这一步就被排除了，所以后面的 map 不会再接到它。只有六十和八十进入加一的步骤，最后被 collect 收进新的动态数组。

读迭代器链时，可以在纸上给每一步写出暂时的结果，先检查顺序，再检查引用和所有权。熟练以后，许多原本需要维护临时数组的 for 循环，就可以用一条清楚的处理链表达。是否使用链式写法，以能否清楚表达规则为准，不必为了看起来简短就把所有操作挤在一起。

```rust
fn main() {
    let scores = vec![50, 60, 80];
    let result: Vec<i32> = scores.iter().copied()
        .filter(|score| *score >= 60)
        .map(|score| score + 1)
        .collect();
    println!("{result:?}");
}
```

结果：
```text
[61, 81]
```

### 智能指针 · 00:38:04

两个计数分别是三和一。在内部作用域中，first、second、third 都拥有同一份数据，所以强引用数是三。离开内部作用域，second 和 third 释放各自的句柄，只剩下外面的 first。

注意，这并不是复制了三份八十，再在作用域结束时合并回一份。它从头到尾共享同一份数据，只是拥有者的数量变化。Box、Rc、Arc 和 RefCell 各自解决不同的问题，先从需要的管理方式出发选择，而不是看到“智能”两个字，就认为包装层数越多越好。

```rust
use std::rc::Rc;
fn main() {
    let first = Rc::new(80);
    {
        let second = Rc::clone(&first);
        let third = Rc::clone(&second);
        println!("{}", Rc::strong_count(&third));
    }
    println!("{}", Rc::strong_count(&first));
}
```

结果：
```text
3
1
```

### 多线程 · 00:45:14

这句话不对。A 在前或者 B 在前都有可能，因为主线程的打印发生在等待之前，并没有与子线程的打印建立固定先后关系。join 保证调用它的线程在这里等待子线程结束，不会倒过来重排之前的输出。

这道题最重要的结论是，不根据一次运行结果猜调度。先检查数据由谁拥有，线程之间怎样通信或加锁，最后在需要结果的位置明确等待。遇到共享数据时，先区分共享拥有和共享修改，很多看起来复杂的多线程代码就能拆开理解。

```rust
use std::thread;
fn main() {
    let job = thread::spawn(|| println!("A"));
    println!("B");
    job.join().unwrap();
}
```

结果：
```text
允许：A → B
允许：B → A
```

### 宏 · 00:50:35

两行分别是十五和零，不会因为第二次没有数字就编译失败。因为规则中的星号允许重复零次，而展开结果一开始就有一个零。三个数字时，后面追加三次加法；没有数字时，后面不追加任何东西。

请注意，这个结论来自当前这条规则。并不是所有宏都必须接受零个参数。换成要求至少一个输入的规则，允许的调用方式就会改变。读宏时把匹配规则和展开结果都看一遍，再判断最终代码，比只看调用的外形更可靠。

```rust
macro_rules! total {
    ($($value:expr),* $(,)?) => {
        0 $(+ $value)*
    };
}
fn main() {
    println!("{}", total!(4, 5, 6));
    println!("{}", total!());
}
```

结果：
```text
15
0
```
