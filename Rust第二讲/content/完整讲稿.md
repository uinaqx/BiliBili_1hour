## 01 类型转换 · conversions

### 01-1 数值类型与显式转换

【画面】类型不同，需要明确转换；as 产生目标类型的值；原来的整数仍可使用

```rust
fn main() {
    let score: u8 = 80;
    let wide = score as u32;
    println!("{score} {wide}");
}
```

【口播】
假设我们有一个八位无符号整数，表示一名学生的分数。另一个函数需要的，却是三十二位无符号整数。虽然它们保存的都是整数，Rust 也不会因为看起来差不多，就自动把两种变量当成同一种类型。我们需要明确告诉编译器，这里要进行转换。

先看 as 这种写法。左边是原来的值，右边写目标类型。这里把八十分转换成更宽的整数，转换后的变量保存的仍然是八十。原来的 score 也还能使用，因为这类整数可以直接复制。as 在这里不是把变量重新命名，也不是修改原变量的声明类型，而是产生一个目标类型的值。

如果你写过 C 或 C++，可以把它先对应到显式的数值类型转换。不过不要据此认为任何 as 转换都能保留原值。接下来我们就看，目标类型装不下时会发生什么。

【运行或检查结果】
```text
80 80
```

### 01-2 窄化转换与数值截断

【画面】300 无法完整放进 u8；as 不返回转换失败；浮点转整数不等于四舍五入

```rust
fn main() {
    let large: u16 = 300;
    let small = large as u8;
    let rounded = 88.9_f64 as i32;
    println!("{small} {rounded}");
}
```

【口播】
现在把问题反过来。三百能放进十六位无符号整数，却放不进八位无符号整数，因为后者最大只能表示二百五十五。代码仍然写 as，这次程序会不会因为装不下而返回一个错误呢。答案是不会。

对于这里的无符号整数窄化，Rust 会保留低位，结果得到四十四。你可以用三百减去二百五十六来理解这个例子。这种转换不会自动替你检查原值是否能够完整保存，所以程序可以编译，却已经失去了原来的三百。

再看浮点数转整数。这里八十八点九转换后得到八十八，去掉了小数部分，并不是四舍五入得到八十九。我们的例子只讨论这个正常范围内的正数，不需要现在记住所有边界规则。先记住最有用的一条：需要保证数值完整时，不要只看到 as 能编译就放心。

【运行或检查结果】
```text
44 88
```

### 01-3 From 与 Into

【画面】From：从给定值构造；Into：由当前值转换；必要时标明目标类型

```rust
fn main() {
    let score: u8 = 80;
    let wide_one = u32::from(score);
    let wide_two: u32 = score.into();
    let name = String::from("小林");
    println!("{wide_one} {wide_two} {name}");
}
```

【口播】
如果转换本来就可以可靠完成，我们常用 From 或 Into，让代码更直接地表达“由这个值构造另一个类型”。画面第一处用目标类型调用 from，把八位整数变成三十二位整数。这种从小范围整数到大范围整数的转换，不会丢掉原来的数值。

第二处调用 into，意思相同，只是从原来的值出发。因为右边没有写目标类型，我们在左边给 wide_two 标上类型，让编译器知道想转成什么。这两行最后都得到八十。先把这两种形式读顺就够了，不必马上自己实现对应的特征。

还要留意，转换不只发生在数字之间。由一段借来的文字创建 String，也可以用 from。但是 String 的转换涉及拥有数据，不能照搬刚才整数可以复制的结论。判断原变量还能不能使用，仍然要看具体类型的所有权规则。

【运行或检查结果】
```text
80 80 小林
```

### 01-4 TryFrom 与可失败的转换

【画面】成功得到 Ok；失败得到 Err；不会把 300 悄悄变成 44

```rust
fn main() {
    let value: u16 = 300;
    match u8::try_from(value) {
        Ok(n) => println!("转换成功: {n}"),
        Err(_) => println!("超出范围"),
    }
}
```

【口播】
刚才三百转换成八位整数时，我们其实想问的是：如果放得下，就给我转换结果；放不下，就明确告诉我失败。这正是 TryFrom 这类写法适合表达的事情。注意它的名字中有 try，但它不是 C++ 里的异常处理语法。

这里调用八位整数的 try_from。转换成功时，结果是 Ok，里面放着八位整数。转换失败时，结果是 Err，里面放着失败的信息。我们用已经熟悉的 match，分别处理两种情况。对于三百，程序会进入失败分支，显示超出范围，而不是悄悄得到四十四。

Ok 和 Err 组成的类型叫 Result。下一章错误处理会更完整地介绍它。此刻先记住，TryFrom 让转换失败成为一个需要处理的结果。如果转换内容关系到成绩、长度或数量，这样显式检查通常更符合我们的本意。

【运行或检查结果】
```text
超出范围
```

### 01-5 字符串解析与结果类型

【画面】parse 按目标类型解析；解析文字可能失败；数字转文字可用 to_string

```rust
fn main() {
    let input = "85";
    match input.parse::<u32>() {
        Ok(score) => println!("成绩: {score}"),
        Err(_) => println!("请输入有效整数"),
    }
}
```

【口播】
从输入框或者文件读到的成绩，通常先是一段文字。文字八十五，不会因为看起来像数字，就自动变成整数。我们需要解析，也就是按照数字的格式理解这段文字。Rust 为字符串提供了 parse 方法。

画面用尖括号明确指定，希望得到无符号的三十二位整数。解析成功时，Ok 里面就是八十五。如果输入换成字母，或者是不符合该类型要求的数字，解析就可能失败，因此 parse 也返回 Result。现在我们仍然用 match，自己决定成功和失败时分别显示什么。

请把两个方向分开。数字变成文字，可以使用 to_string；文字想成为数字，则需要解析，而且可能失败。parse 不是直接强行改变字符串的内存解释方式。实际程序中，这个区别十分有用：我们不能仅靠输入框提示“请输入数字”，就假设用户永远输入正确。

【运行或检查结果】
```text
成绩: 85
```

## 02 模块 · modules

### 02-1 模块与命名空间

【画面】mod 组织相关代码；:: 表示路径；模块不是线程

```rust
mod grades {
    pub fn passed(score: u32) -> bool {
        score >= 60
    }
}
fn main() {
    println!("{}", grades::passed(80));
}
```

【口播】
程序只有几行时，把所有函数放在一起还没有问题。随着功能增多，成绩处理、文字显示和输入检查混在同一层，找函数就越来越费劲。模块可以把相关的代码放在一起，并给它们一个共同的路径。

这里用 mod 声明一个叫 grades 的模块，把及格判断函数放在里面。调用时写模块名、两个冒号，再写函数名。你可以把这个路径看成是在说明，我们要找的是成绩模块里的及格判断。Rust 模块不是运行时启动的一项任务，也不会因为写了模块就多出一个线程。

对于学过 C++ 的同学，这里可以先联系命名空间来理解代码分类。但 Rust 模块还和文件组织、可见性规则联系在一起，并不只是起一个分类标签。先把最短的模块和调用路径看明白，再去看哪些内容能在模块外使用。

【运行或检查结果】
```text
true
```

### 02-2 默认私有与 pub

【画面】默认私有；pub 明确公开接口；先核对访问路径

```rust
mod grades {
    fn passed(score: u32) -> bool { score >= 60 }
}
fn main() {
    println!("{}", grades::passed(80));
}
```

【口播】
请把目光放到 pub 上。刚才的函数前面有 pub，现在去掉它，再从模块外调用，会发生什么。编译器会拒绝这次调用，因为这个函数在这里是模块内部的内容。Rust 中很多项目默认是私有的，需要明确公开，模块外的代码才可以沿相应路径使用。

不要把私有理解成加密或者保护密码。这里主要是在规定程序内部哪些地方能使用这段代码，使模块的使用边界更清楚。成绩模块可以把内部的辅助计算藏起来，只公开真正希望别人使用的函数。这样以后修改内部实现，调用者未必需要跟着修改。

现在的例子只涉及从父模块访问子模块的函数，先掌握这个最常见的方向。看到无法访问的错误时，检查调用路径和可见性，不要遇到问题就给每一个东西都加 pub。公开的接口越多，后续需要长期保持稳定的约定也就越多。

【运行或检查结果】
```text
编译失败：函数 passed 为私有
```

### 02-3 use 与路径简化

【画面】use 简化当前作用域的名字；不会复制代码；crate 从当前 crate 根开始

```rust
mod grades {
    pub fn passed(score: u32) -> bool {
        score >= 60
    }
}
use crate::grades::passed;
fn main() {
    println!("{}", passed(59));
}
```

【口播】
如果一页代码里多次调用同一个模块的函数，每次都写完整路径会比较啰嗦。use 可以把一个现有路径引入当前作用域，让后面的使用更简短。这里把成绩模块的及格判断引入后，就可以直接写 passed。

use 不会把函数复制一份，也不会把另一个文件当作文本粘贴进来。它主要改变我们怎样在当前作用域中找到一个名字。原来的完整路径依然可以使用。你熟悉 C++ 的 using 时，可以借这个联系来理解，但不要把它和头文件的文本包含混为一谈。

这条路径前面的 crate 表示从当前这个编译单元的根位置开始找。暂时可以把它理解成从当前项目这一侧的起点往下找。以后遇到更深的模块，还会看到 super 表示上一级，self 表示当前模块。现在不需要把所有组合背下来，先用清楚的路径定位到目标。

【运行或检查结果】
```text
false
```

### 02-4 模块与多个源文件

【画面】main.rs 声明 mod grades;；grades.rs 保存模块内容；不是头文件文本包含

```rust
mod grades;
fn main() {
    println!("{}", grades::passed(80));
}
```

【口播】
模块中的代码继续增多时，可以把它放到另一个源文件中。画面现在是主文件。注意 mod grades 后面直接是分号，没有花括号，这表示模块的内容放在约定的外部文件位置。我们这个最简单的项目，把 grades 点 rs 放在主文件旁边。

这个文件里面写的是函数本身，不需要再把全部内容包在另一个同名的 mod 里。否则相当于又增加一层模块。对于这里的普通布局，主文件和成绩文件放在同一个源代码目录，再在主文件里声明模块，Rust 就知道去哪里找它。

这和 C 或 C++ 常见的头文件包含方式不同。我们是在声明模块树和寻找模块源文件，不是让预处理器把文件文本直接替换进来。实际项目还有目录形式的模块布局，这节先掌握这一对文件。完整的两个文件都放在配套示例里，可以直接编译验证。

### 02-5 公开结构体与字段边界

【画面】类型与字段分别控制可见性；只公开必要操作；私有字段通过方法读取

```rust
pub struct Student {
    pub name: String,
    score: u32,
}
impl Student {
    pub fn new(name: String, score: u32) -> Self {
        Self { name, score }
    }
    pub fn score(&self) -> u32 { self.score }
}
```

以上为节选；配套示例包含完整可编译上下文。

【口播】
最后再看一个容易误会的地方。结构体前面有 pub，是否说明它的每一个字段都已经公开了。不是。结构体类型和字段的可见性需要分别考虑。我们可以公开 Student 这个类型，却不允许外部直接改它保存的成绩。

画面里的结构体放在 school 模块中。name 字段是公开的，score 字段没有公开。模块外可以读姓名，却不能直接读取这里的私有成绩字段。这样的设计可以让成绩的修改统一经过某个方法，以便以后加入范围检查。这里先通过创建方法建立学生，再用公开的方法读取成绩。

这一节最值得记住的不是把 pub 到处加上，而是区分模块内部的实现和模块对外提供的用法。把数据分好类，再只公开必要的操作，程序变大时会更容易理解和维护。

【运行或检查结果】
```text
小林 80
```

## 03 错误处理 · error_handling

### 03-1 Option 与 Result 的区别

【画面】Option 表示有或没有；Result 表示成功或失败原因；Ok 与 Err 互斥

```rust
fn check(score: u32) -> Result<u32, &'static str> {
    if score <= 100 { Ok(score) }
    else { Err("成绩超过100") }
}
fn main() {
    println!("{:?}", check(80));
    println!("{:?}", check(120));
}
```

【口播】
上一部已经介绍过 Option，它表示有没有一个值。比如没有找到学生，可以得到 None。但有些操作失败时，我们还想知道为什么失败，单纯说没有结果就不够了。Result 正是用来表示成功的结果，或者失败的原因。

画面中，检查成绩的函数返回 Result。成功时，Ok 里面放着有效成绩；失败时，Err 里面放着一句说明。这里的成功值是整数，错误值是借来的固定文字，所以返回类型里同时写出这两种类型。尖括号中的第一个位置是成功类型，第二个位置是错误类型。

你可以把它先读成：这个函数要么给我一个有效成绩，要么给我一个失败说明。它与 C 语言常见的错误码约定有所不同，成功和失败在类型中就被明确分开。调用者看见返回类型，就应该意识到不能只考虑成功的情况。

【运行或检查结果】
```text
Ok(80)
Err("成绩超过100")
```

### 03-2 match 处理成功与失败

【画面】失败可以被处理；match 覆盖两种结果；处理后可以继续执行

```rust
fn main() {
    match "hello".parse::<u32>() {
        Ok(score) => println!("成绩: {score}"),
        Err(_) => println!("输入不是有效整数"),
    }
    println!("程序继续运行");
}
```

【口播】
得到 Result 以后，最容易看清控制过程的办法，仍然是 match。我们把可能成功或失败的操作放在前面，再分别写 Ok 和 Err 两个分支。这里尝试把一段非数字文字解析成成绩，失败时只显示一条友好的提示。

请注意，失败不一定意味着程序必须崩溃。我们完全可以告诉用户重新输入，然后继续执行其他代码。具体应该怎样处理，取决于这个程序的目标。比如输入不合法是常见情况，给出提示通常比直接让程序终止更合适。

这段代码之后还有一句程序继续运行，运行结果也能看见它。也就是说，我们确实处理了失败，而不是假装失败从未发生。先把这种展开写法练熟，后面看到更短的形式，就更容易理解它省掉了哪些重复的步骤。

【运行或检查结果】
```text
输入不是有效整数
程序继续运行
```

### 03-3 问号运算符与错误传播

【画面】成功取出值并继续；失败提前返回 Err；问号不提供默认值

```rust
use std::num::ParseIntError;
fn parse_score(text: &str) -> Result<u32, ParseIntError> {
    let score = text.parse::<u32>()?;
    Ok(score + 1)
}
fn main() {
    println!("{:?}", parse_score("80"));
    println!("{}", parse_score("abc").is_err());
}
```

【口播】
如果一个函数要连续完成几项可能失败的操作，每一项都写一大段 match，会比较重复。问号运算符可以表达一种常见选择：这一步成功，就取出成功值继续；这一步失败，就立刻把错误交给调用者。

看 parse_score 里面的第一行。parse 后面的问号，不是把失败忽略掉，也不是返回一个默认的零。解析成功时，score 得到整数。解析失败时，函数在这里就返回错误，不会继续走到下一行。调用这个函数的地方，仍然要决定如何处理返回的 Result。

所以问号适合放在返回相容结果类型的函数里。画面用的错误类型，就是标准库整数解析会产生的错误类型。这里先不展开不同错误类型之间如何转换。只要牢牢记住，问号是把处理失败的责任向外传，不是把责任取消了。

【运行或检查结果】
```text
Ok(81)
true
```

### 03-4 map_err 与业务范围检查

【画面】先解析，再检查范围；map_err 只转换错误；问号仍然负责传播

```rust
fn read_score(text: &str) -> Result<u32, &'static str> {
    let n = text.parse::<u32>()
        .map_err(|_| "请输入整数")?;
    if n > 100 { return Err("成绩超过100"); }
    Ok(n)
}
fn main() {
    println!("{:?}", read_score("abc"));
    println!("{:?}", read_score("120"));
}
```

【口播】
实际程序经常要完成两层检查。第一层，输入能否理解成整数。第二层，这个整数是否在允许的成绩范围内。能解析成一百二十，不代表它就是有效成绩。我们可以把这两层检查都放进一个函数。

这里先用 map_err，把标准库返回的解析错误，换成适合当前程序的一句说明。这个名字可以直观地理解为，只转换错误这一边，成功值并不因为它发生改变。后面的问号再把失败及时交出去。成功解析后，程序继续检查有没有超过一百分。

这样调用者拿到的是同一种错误类型，却能看到两种不同原因。我们这次用固定文字，让例子保持短小。以后需要携带更多错误细节时，可以设计自己的错误枚举。现在先把“解析失败”和“业务规则不符合”这两件事分开理解，不要混成一种问题。

【运行或检查结果】
```text
Err("请输入整数")
Err("成绩超过100")
```

### 03-5 unwrap、expect 与 panic

【画面】unwrap 要求结果一定成功；expect 失败时同样 panic；外部输入应认真处理错误

```rust
fn main() {
    let score = "abc".parse::<u32>().unwrap();
    println!("{score}");
}
```

【口播】
有时你会看到别人直接调用 unwrap，把 Ok 里面的值拿出来。它确实很简短，但前提是结果必须成功。如果里面是 Err，程序就会发生 panic。expect 也会在失败时 panic，只是允许写一段更具体的说明。

画面故意把无法解析的文字交给 parse，再立刻 unwrap。这段代码可以通过编译，但运行时会失败。编译通过，说明类型等规则满足要求，并不说明所有输入下都能正常运行。请把这两种失败分清：编译错误发生在程序运行之前，panic 发生在执行过程中。

练习中，已经确认不会失败的常量例子，偶尔用 unwrap 可以让代码更短。但面对用户输入、文件读取或其他本来就可能失败的操作，应该认真决定如何返回或处理错误。不要把所有 Result 都立即 unwrap，否则前面设计出的失败信息，就没有得到好好利用。

【运行或检查结果】
```text

```

## 05 迭代器 · iterators

### 05-1 迭代器与 next

【画面】iter 借来逐个读取；next 推进当前进度；取完以后返回 None

```rust
fn main() {
    let scores = vec![60, 80];
    let mut items = scores.iter();
    println!("{:?}", items.next());
    println!("{:?}", items.next());
    println!("{:?}", items.next());
}
```

【口播】
处理一组成绩时，最直观的办法是一次取出一个，处理完再取下一个。迭代器就提供了这样一套逐个访问的方式。对动态数组调用 iter，会得到一个借来读取元素的迭代器。它不是把原来的成绩数组复制一份。

这里手动调用 next。前两次分别得到 Some，里面放着对应元素的引用。元素用完以后，再调用 next，就得到 None。因为取元素会改变当前进度，手动保存的迭代器要声明为可变。平常写 for 循环时，Rust 已经在背后使用迭代器协议，所以我们通常不需要亲手反复调用 next。但看清这个最小过程，有助于理解后面的各种组合。

【运行或检查结果】
```text

Some(80)
None
```

### 05-2 闭包与 map

【画面】闭包描述逐项处理规则；map 产生新元素；collect 决定收集结果

```rust
fn main() {
    let scores = vec![60, 80];
    let updated: Vec<i32> = scores.iter()
        .map(|score| *score + 5)
        .collect();
    println!("{updated:?}");
    println!("{scores:?}");
}
```

【口播】
接下来想给每一个分数加五分，得到一组新成绩。map 可以描述“每个元素怎样变成新元素”。它接收一小段处理规则，这种可以写在使用位置的规则，叫作闭包。竖线里面是参数，竖线后面是处理过程。

这里 iter 给出的元素是引用，所以用星号读出分数，再加五。map 描述转换规则，collect 才把逐个产生的新分数收集成动态数组。左边标出 Vec 的元素类型，帮助编译器确定收集成什么。最后的新数组是六十五和八十五，原来的六十和八十仍然保留。先把它看成“借来读，计算新值，再收集”，不必急着记住所有闭包类型。

【运行或检查结果】
```text

[60, 80]
```

### 05-3 filter 与组合顺序

【画面】filter 保留条件成立的元素；按链条顺序逐步阅读；先后顺序可能改变结果

```rust
fn main() {
    let scores = vec![50, 60, 80];
    let result: Vec<i32> = scores.iter().copied()
        .filter(|score| *score >= 60)
        .map(|score| score + 1)
        .collect();
    println!("{result:?}");
}
```

【口播】
除了逐项转换，我们也经常想只留下符合条件的元素。filter 就负责筛选：判断成立就保留，不成立就跳过。这里先借来访问，再用 copied 把可复制的整数取出来，接着筛选及格成绩，最后再统一加一分。

请按从上到下的顺序读这条处理链。五十分先被筛掉，六十和八十保留下来，再变成六十一和八十一。filter 在判断时借来检查当前整数，所以闭包里仍用星号读取它。最重要的是，每一步处理的对象和先后顺序都要清楚。先加分再筛选，与先筛选再加分，可能产生不同结果，不能只看方法名称相同就认为等价。

【运行或检查结果】
```text
[61, 81]
```

### 05-4 惰性求值与消费操作

【画面】map 先描述规则；需要消费操作推动处理；没有消费，就没有逐项执行

```rust
fn main() {
    let scores = vec![60, 80];
    let _pending = scores.iter().map(|score| {
        println!("处理: {score}");
        *score + 1
    });
    println!("只创建了规则");
}
```

【口播】
迭代器有一个很重要的特点，叫惰性。这个名字听起来抽象，意思其实是：只把逐项处理的规则写出来，不一定已经真正处理了元素。看看这里，map 的闭包中有打印，但我们没有开始逐项取值，也没有收集结果。

运行时只会显示“只创建了规则”，不会显示“处理六十”或者“处理八十”。如果用 for 去遍历，或者调用 collect、sum 等需要结果的操作，才会推动前面的逐项处理。你可以把 map 看成先准备好一道工序，后面有人真正需要产物时，这道工序才开始工作。这样也能解释，为什么只写了一条转换链却没使用结果时，程序看起来像什么也没发生。

【运行或检查结果】
```text
只创建了规则
```

### 05-5 iter、iter_mut 与 into_iter

【画面】iter：读取；iter_mut：修改；into_iter：对 Vec 交出集合

```rust
fn main() {
    let mut scores = vec![60, 80];
    for score in scores.iter_mut() {
        *score += 1;
    }
    println!("{scores:?}");
    let total: i32 = scores.into_iter().sum();
    println!("{total}");
```

【口播】

### 05-6 迭代器与所有权错误

### 06-2 Box 与递归类型

### 06-3 Rc 与共享所有权

## 07 多线程 · threads

### 07-1 线程创建与 join

【画面】spawn 创建线程；join 等待该任务结束；等待之后的语句才继续

```rust
use std::thread;
fn main() {
    let job = thread::spawn(|| {
        println!("子线程任务完成");
    });
    job.join().unwrap();
    println!("主线程等待结束");
}
```

【口播】
线程可以让程序里的不同任务并发进行。并发不等于每一条指令都在同一时刻运行，实际安排由系统调度。先看最短的写法：thread 的 spawn 创建一个新线程，竖线之间没有参数，后面的花括号就是它要做的事情。

spawn 会返回一个句柄，我们可以通过它调用 join，等待这项任务结束。画面先等子线程，再显示等待结束，所以这里两行输出的顺序有保证。join 也可能返回线程失败的信息，示例为了突出等待过程，用 unwrap 假设任务正常结束。真正程序中，是否允许这种失败，还需要像其他 Result 一样认真处理。

### 07-2 执行顺序与调度

【画面】join 前的两次打印顺序不保证；一次运行不能证明固定顺序；只根据明确等待关系判断

```rust
use std::thread;
fn main() {
    let job = thread::spawn(|| println!("A"));
    println!("B");
    job.join().unwrap();
}
```

【口播】
现在把主线程的打印放到 join 前面。请注意，先写 spawn，不代表子线程一定先打印。子线程显示 A，主线程显示 B，哪一个先发生，取决于实际调度。两种顺序都有可能，不能靠自己电脑上运行的一次结果作保证。

join 在这里能保证的是，主线程等待子线程结束以后，才继续往下走。它不会把前面已经发生的打印重新排序。教学画面列出的两种顺序，是允许的可能结果，不是同时打印四行。写多线程程序时，先找代码中真正建立的先后关系，不要把源代码的书写位置当作所有线程共享的一张执行时间表。

### 07-3 move 闭包与数据所有权

【画面】move 带入需要的外部值；Vec 的所有权进入子线程；join 可取得线程返回值

```rust
use std::thread;
```

【口播】
如果子线程要使用主线程创建的数据，就需要想清楚，这份数据由谁负责保存，能存活到什么时候。move 闭包可以把需要拥有的外部值带进闭包，让新线程负责使用。这里把动态数组交给子线程，在里面求和并返回总分。

join 等待任务结束，也把线程返回的整数带回来，所以最后可以显示一百四十。这里 move 带走了 Vec 的所有权，外面不能再把原来的 scores 当完整集合使用。不要把 move 读成“把每个值都深拷贝一份”。遇到可以复制的整数时，行为又要结合 Copy 来判断。所有权规则并没有因为进入多线程就换成另一套。

### 07-4 通道与消息传递

【画面】channel 创建发送端与接收端；send 发送，recv 接收；接收可能等待，也可能失败

【口播】

这里把发送端移动进子线程，发送八十五。主线程调用 recv，等待接收到一个值，然后显示它。send 和 recv 都可能失败，所以也返回 Result。这个例子中我们保证对应的两端还在，再用 unwrap 简化展示。通道适合把数据从一侧交给另一侧；发送拥有所有权的数据时，也要考虑数据是不是随消息一起被移动。我们先掌握一条消息的流程，不展开复杂的多生产者结构。

### 07-5 Mutex 与互斥访问

【画面】lock 成功后取得守卫；通过守卫修改数据；守卫离开时自动解锁

```rust
use std::sync::Mutex;

    {

        *guard += 5;

}
```

【口播】
除了发消息，有时几项任务必须修改同一份数据。Mutex 可以规定，同一时刻只有拿到锁的一方进入受保护的修改过程。先在单线程里看它怎么用，这样不会同时混进线程调度的问题。

lock 成功后，会得到一个守卫。通过守卫读写里面的值，守卫离开作用域时，锁自动释放。画面特意用一对花括号把加分过程包起来，再在外面重新加锁读取。不要把锁拿得过久，也不要拿着同一个锁，又在同一条执行路径上等待自己重新取得它。锁解决的是有秩序地访问，不是把任何程序都自动变成既正确又高效的并发程序。

以上为节选；配套示例包含完整可编译上下文。

【口播】
这一页接着看程序的收尾。主线程把所有线程句柄都取出来，逐一调用 join。只有这些任务都正常完成之后，才加锁读取最终计数。两个线程各做一百次加一，所以这次最终结果确定为二百。

如果没有等到所有工作完成，就提前读取，看到的可能只是中间结果。即使每次加一都有锁，也不能因此省去对完成时机的安排。这里锁保护了修改过程，join 保证了我们读取之前工作已经结束，两项条件共同支持最终的结论。多线程不一定更快，创建线程、加锁和等待都有成本，小任务尤其要根据实际需要选择。

【运行或检查结果】

### 07-q 多线程：课堂练习

【画面】spawn 的位置是否决定打印顺序；join 等待的是哪项任务；列出允许的两种顺序

```rust
use std::thread;
fn main() {
    let job = thread::spawn(|| println!("A"));
    println!("B");
    job.join().unwrap();
}
```

【口播】
请回到刚才的打印例子。子线程打印 A，主线程先打印 B，再调用 join。有人说，因为 spawn 写在前面，所以一定先看到 A。这句话对吗。请判断哪些顺序是允许的，并说明 join 到底保证了什么。思考四秒钟。

【思考停顿】4 秒

### 07-a 多线程：答案解析

【画面】两种顺序都允许；join 之前没有固定先后；不要用一次运行推断保证

```rust
use std::thread;
fn main() {
    let job = thread::spawn(|| println!("A"));
    println!("B");
    job.join().unwrap();
}
```

【口播】
这句话不对。A 在前或者 B 在前都有可能，因为主线程的打印发生在等待之前，并没有与子线程的打印建立固定先后关系。join 保证调用它的线程在这里等待子线程结束，不会倒过来重排之前的输出。

这道题最重要的结论是，不根据一次运行结果猜调度。先检查数据由谁拥有，线程之间怎样通信或加锁，最后在需要结果的位置明确等待。遇到共享数据时，先区分共享拥有和共享修改，很多看起来复杂的多线程代码就能拆开理解。

【运行或检查结果】

## 08 宏 · macros

### 08-1 宏调用与函数调用

【画面】宏按规则展开代码；感叹号提示宏调用；普通函数够用时优先用函数

```rust
fn main() {
    let scores = vec![80, 85];
    println!("学生人数: {}", scores.len());
    assert_eq!(scores[0], 80);
}
```

【口播】
我们已经用过 println、vec 和 assert 这些带感叹号的写法。它们是宏。先用一句话理解它：宏可以根据写法规则，在编译过程中展开出代码。普通函数通常接收已经求出的参数值，而宏能够按照输入的代码形式生成相应的代码。

所以 println 可以接收不同数量的格式化参数，vec 也能接收一组元素。它们并不是因为名字后面随意加了感叹号，就变成某种更快的函数。对初学者，先区分“使用现成宏”和“自己设计宏”。大多数时候，清楚的普通函数已经足够；只有确实需要生成重复代码或特殊调用形式时，再考虑写宏。

【运行或检查结果】
```text
学生人数: 2
```

### 08-2 macro_rules 与表达式匹配

【画面】expr 匹配一个表达式；左边匹配，右边展开；调用时可以传入计算表达式

```rust
macro_rules! show_score {
    ($value:expr) => {
        println!("成绩: {}", $value);
    };
}
fn main() {
    show_score!(85);
    show_score!(80 + 5);
}
```

【口播】
现在自己定义一个很小的宏，专门按统一格式显示成绩。macro_rules 后面写宏的名字，花括号里写匹配规则和展开结果。这里把输入的一段表达式叫 value，expr 说明我们希望匹配的是表达式。

调用宏时，可以传八十五，也可以传八十加五。展开后，输入表达式被放进打印语句中，所以两次都显示成绩八十五。不要把美元符号理解成变量里的真实字符，它是在宏规则中标记需要匹配和替换的部分。初学时先读一条规则：左边允许怎样调用，右边会生成什么代码，再往下看重复匹配。

【运行或检查结果】
```text
成绩: 85
成绩: 85
```

### 08-3 重复匹配与可变参数数量

【画面】* 表示零次或多次重复；每个输入各生成一次加法；本规则允许末尾逗号

```rust
macro_rules! total {
    ($($value:expr),* $(,)?) => {
        0 $(+ $value)*
    };
}
fn main() {
    println!("{}", total!(4, 5, 6));
    println!("{}", total!());
}
```

【口播】
如果想允许传入几个数字，再把它们相加，可以使用重复匹配。画面里，括号中的表达式可以按逗号分隔，出现零次或多次。展开结果先放一个零，再为每一个匹配到的值追加一次加法。

所以传四、五、六时，相当于得到零加四加五加六，结果是十五。没有传数字时，只剩下零，结果也是明确的。后面那个可选逗号的部分，让调用末尾多写一个逗号也能匹配。这些符号看起来比较密，不需要现在凭记忆写出复杂规则。先把这条规则和它接受的调用逐一对应，再判断生成的表达式能否正常使用。

【运行或检查结果】
```text
15
0
```

### 08-4 展开后的求值次数

【画面】输入表达式被展开两次；带副作用时可能执行两次；先检查真正生成的代码

```rust
macro_rules! twice {
    ($value:expr) => { $value + $value };
}
fn main() {
    let mut count = 0;
    let result = twice!({ count += 1; count });
    println!("{result} {count}");
}
```

【口播】
自己写宏时，有一个很值得警惕的地方：同一段输入代码，如果在展开结果里使用两次，可能就被执行两次。这里 twice 把输入表达式放在加号两边。输入不是一个固定数字，而是一段会把计数器加一的表达式。

展开后，左边执行一次得到一，右边再执行一次得到二，所以结果是三，计数器也变成二。如果你原本想先计算一次，再把那个结果乘二，这个宏就没有表达你的本意。宏不是普通函数参数值的简单替代。阅读时要把展开后的代码想出来，尤其关注输入表达式有没有打印、修改计数或其他副作用。

【运行或检查结果】
```text
3 2
```

### 08-5 单次求值与派生宏概览

【画面】先保存输入表达式的结果；本例只执行一次计数增加；宏生成的代码仍需通过检查

```rust
macro_rules! twice {
    ($value:expr) => {{
        let value = $value;
        value + value
    }};
}
fn main() {
    let mut count = 0;
    let result = twice!({ count += 1; count });
    println!("{result} {count}");
}
```

【口播】
要符合刚才“只计算一次”的意图，可以在宏展开的代码块里，先把输入表达式的结果保存起来，再使用这个值两次。这样计数器只增加一次，结果是二，计数器是一。两层花括号让展开结果形成一个自己的代码块，并把最后的表达式作为结果。

另外，上一部用过的 derive 也与宏有关，它让编译过程为类型生成相应实现。Rust 还有过程宏等形式，需要另外的工程组织，这节先认识分类，不动手编写。我们已经能使用常见宏，也能读懂一个简单的声明宏。不要急着用宏替代所有函数，生成的代码仍然必须满足 Rust 的类型和借用规则。

【运行或检查结果】
```text
2 1
```

```rust
    };
```

【口播】

### 08-a 宏：答案解析

```rust

        0 $(+ $value)*
    };

    println!("{}", total!());
```

【口播】

## 10 综合回顾 · Summary

### 10-1 九个主题的使用顺序

【画面】先明确数据与失败路径；再组织、处理并验证行为；并发与宏按真实需要使用

【口播】
现在把今天的内容连成一次实际开发过程。首先，把输入文字转换成需要的类型，注意数值范围和解析失败。接着，用模块把相关功能组织起来，只公开需要使用的接口。可能失败的操作，明确返回 Result，并决定失败由哪一层处理。

写出功能以后，用单元测试核对正常输入、错误输入和边界。处理一组数据时，可以使用迭代器描述筛选、转换和汇总，同时检查借用与所有权。需要间接拥有或共享数据时，再根据目的选择 Box、Rc、RefCell 或 Arc，而不是一开始就把它们全部堆在一起。

如果确实需要多线程，明确任务怎样结束、数据怎样传递，以及共享修改怎样受到保护。需要生成重复代码时，先判断普通函数是否已经足够，再决定是否使用宏。最后，把格式化、编译、测试和 Clippy 检查结合起来，反复验证改动。每一个工具都对应一个具体问题，不需要为了使用新名字而增加复杂度。

### 10-2 练习方法与常见错误

【画面】小程序练习，逐步增加功能；区分编译、运行与行为错误；修改一处，运行一次，解释原因

【口播】
课后练习可以从一小段程序开始。试着把成绩解析函数移进模块，为零分、六十分、一百分和非法文字写测试，再用迭代器筛选并汇总一组有效成绩。先把这个单线程版本写清楚，不必急着改造成大型系统。

遇到错误时，仍然先分类。编译器拒绝了什么，是类型、可见性、移动，还是借用规则。运行时失败了什么，是没有处理的 Result，还是 RefCell 借用冲突。结果不符合预期时，再检查边界、迭代器顺序，以及线程之间是否真正建立了等待关系。

今天最希望你带走的，是一种稳定的读代码方法：先说清楚希望发生什么，再沿着数据和控制流程逐步核对。把每一小段代码亲手运行，改一个条件，观察一个结果，再回头解释原因。九个主题不需要一次全部背熟，能在具体问题里找到合适的工具，就已经迈出了很重要的一步。这节课就到这里。
