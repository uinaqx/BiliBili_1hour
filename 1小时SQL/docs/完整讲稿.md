## 00:00:00 数据库与基础查询

### 00:00:00 从一张订单表开始

同学们好，欢迎来到一小时学完 SQL。想象你负责校园小店。每天进来很多订单，老板问，今天卖了多少，谁买得最多，哪些订单还没付钱。我们会用一套练习数据，把这些问题依次变成可以运行的查询。先看一张表，再学会过滤、排序、分组和连接，最后试着新增、修改和回退一笔订单。每章都有一道预测题，你可以先在纸上写答案，再看屏幕上的结果。

先看第一条查询。FROM 后是订单表的名字，叫 orders。一行保存一笔订单，列用来描述它的不同信息。比如订单号和金额分别是两列。SELECT 指定结果要显示的列。这里屏幕只需要看编号和金额，其他信息留在订单表里。用编号从小到大排列，再只看前三行。你会看到编号一百零一、一百零二、一百零三，对应金额一百二十、八十、六十。

### 00:01:08 运行第一条 SQL

开始动手时，我们使用 SQLite。它适合本地练习，一份数据库可以保存为一个文件。配套工程提供初始化脚本，每道练习都会从同一份初始数据出发。第一条语句很短，SELECT 后放一段单引号中的文字。文字会作为结果显示出来。AS 后面起一个栏目名，读结果时就知道这一列是问候语。

第二列是二加三。数据库先做运算，再把五放进名为 answer 的列。逗号把两个要显示的项目分开，分号标记这条语句已经写完。你可以先把二加三换成四乘六，再运行一次。熟悉这一步之后，后面的练习就用同样的方式操作，每次改一处，先预测结果，再执行和检查。这个习惯在查询复杂之后尤其有用。

### 00:02:03 从客户表选列

客户表叫 customers。这里有四位客户，每位各占一行。每一行存一个唯一编号、姓名和城市。把客户资料放在单独一张表里，订单可以通过编号找到对应的人。先处理一个简单需求，列出所有客户的姓名和城市。我们从第二行开始读，先确定数据来自客户表。

再看 SELECT，先写 name，再写 city，结果第一列是姓名，第二列是城市。如果互换书写位置，屏幕上的两列也会互换。这里没有把编号选进结果，底下的表仍然保存编号。最后用编号排序，看到的是小林、小周、小陈、小吴。把一张表从左到右看叫看列，从上到下看叫看行。接下来的过滤专门决定哪些行能进入结果。

### 00:03:02 用星号浏览表的结构

第一次遇到陌生表时，可以先用 SELECT 星号看结构。这里星号会展开订单表里的所有列，从编号到优惠码都会出现。一行的内容可以理解成一张订单单据。编号识别订单，客户编号找人，金额用整数存储，状态用文字存储，日期和优惠码也各有一栏。这次依然从 orders 读取，按照编号排列，只看前两笔。

看看结果的最后一列。第一笔用的是 NEW10，第二笔屏幕上显示 NULL，意思是这一笔的优惠码是空值。后面会专门用一页查询这种记录。星号适合快速看数据结构。写给别人用的报表时，列出明确列名，能让报表只显示需要的信息，也让列的排列方式更容易掌握。

### 00:03:57 给计算结果起名字

现在假设每笔订单要按五元配送费做一个报价。我们先把编号和原金额选出来，再增加一项金额加五。为了方便看懂，给新列起名 with delivery，表示含配送费的报价。逗号连接三项结果，第二行和第一行仍然属于同一个 SELECT。

查询从订单表读数据，按编号取前三笔。第一单原金额一百二十，报价是一百二十五。第二笔是八十和八十五，第三笔是六十和六十五。这一列的计算发生在查询结果里。重新运行前一页的订单查询，原始金额依然是表中保存的数值。这个写法可以用来预演费用计算，之后也能把多个计算放在同一张结果表里核对。

## 00:05:51 条件筛选与空值

### 00:05:51 用 WHERE 保留符合条件的行

要找金额至少一百二十元的订单，先写出要显示的编号和金额，再指出来源是 orders。现在表里有八行，希望数据库替我们逐行比较金额。WHERE 后放比较条件。大于号后面有等号，所以一百二十自身也过关。想象订单经过一个筛子，金额到一百二十的留下，较小的金额继续留在原表里。

按编号查看输出，可以找到一百零一、一百零四、一百零五、一百零六。金额分别是一百二十、二百、一百二十、一百六十。这里一百零五是已取消的订单，因为本页筛选只看金额。要排除已取消的行，可以再补充一个状态条件。写查询前先把口头要求里的限制读一遍，金额、时间和状态都可能各需要自己的条件。

### 00:06:48 同时满足两个条件

这一次老板只看已经收到的钱。结果多显示状态一列，方便一边看金额一边验证。WHERE 后先检查金额条件，再用 AND 连上状态等于已支付。两个条件都成立的订单才会进入结果。文字用单引号，等号表示比较。用换行把多个条件排开，读的时候很容易看出各自负责哪一项要求。

编号一百零五金额够了，状态却是已取消，于是被筛掉。编号一百零二已经支付，金额八十，也被筛掉。这两个例子分别覆盖了两项条件之一失败的情况。按编号看最后三笔记录，一百零一、一百零四、一百零六。如果结果比预期少，可以先分别试两项条件，再加回 AND，看看哪一项筛掉了那笔订单。

### 00:07:45 用括号规定 OR 的范围

有时一个需求会给出两种可能。比如客服想检查待支付或已取消、并且金额小于一百的订单。先把两种状态用 OR 连起来，再把它们括成一组。每一行只要属于其中一种状态，这一组就通过。接着用 AND 加金额限制。按这个顺序读，先判状态组，再看金额是否达标。

初始数据里，一百零三和一百零八是待支付，一百零五是已取消。已取消这一笔金额一百二十，过不了小于一百的限制，所以结果剩一百零三和一百零八。这对括号影响的是条件组合。如果删掉括号，SQL 会先算 AND，金额限制只会和后面的已取消组合。写包含 AND 和 OR 的条件时，用括号直接表达业务分组。

### 00:08:38 用范围选择日期

要取六月订单，先选编号和下单日期。练习数据里日期统一写成四位年、两位月、两位日。这个固定格式可以直接按文字顺序比较日期。从六月一日开始，允许包含当天，再以七月一日为上界，取严格小于上界的日期。这样两个月份之间的边界各归一边。

结果按日期排列，日期相同就用编号决定顺序。屏幕上有六月一日、二日和三日各一笔。七月一日的订单留给七月报表。这个范围写法也适合带时分秒的字段，前提是存储或比较使用一致的格式。想查七月，就把起点和终点各向后推一个月，其他代码可以沿用。

### 00:09:31 用 IS NULL 查缺失值

再看订单的优惠码。有些订单没有优惠码，我们用 IS NULL 找出这一类数据。NULL 表示缺失。从练习表的前三笔里找，编号限制是一百零三及以前。顺着数据看，第一笔有 NEW10，第二笔和第三笔是空值，所以留下后二者。

为了让结果好读，用 COALESCE 从两个值里挑第一个存在的值。优惠码存在就用优惠码，遇到空值就显示无。结果这两笔都显示无。原表里仍然保留空值，之后再用 IS NULL 还能查到这些订单。要查使用了优惠码的订单，可以用 IS NOT NULL。把空值查询和显示替代分开写，统计和界面就能使用各自合适的表达。

### 00:10:21 练习 · 找出符合组合条件的订单

这道题给两条规则。状态是已支付或待支付，金额在八十到一百二十元之间。IN 后放一组允许的状态。订单状态只要是括号中的某一个就通过。BETWEEN 从八十到一百二十，包含两端。停几秒，先从八行里找金额合适的，再去掉状态不符合的，写下留下的订单编号。

金额合适的是编号一百零一、一百零二、一百零五、一百零七和一百零八。一百零五是已取消的订单，状态不在名单里，去掉。最后四个编号按顺序是第一、第二、第七和第八笔。这里按编号排序。可以发现八十元和一百二十元都在结果里。边界题最容易少算一项，做查询时记得挑一个刚好等于上界和下界的值测试。

## 00:11:22 排序、分页与表达式

### 00:11:22 从大到小排列订单

想看看金额最高的几笔订单，先选出编号和金额，从订单表读取。ORDER BY 后列排序键。金额后写 DESC，金额从大到小。等金额相同，再按照编号从小到大，所以编号后面写 ASC。一笔记录的排序位置由这两个键一起决定。想要显示得稳定，常用唯一编号作为最后一个排序键。

最后限制四行。结果先是二百，再是一百六十，接着出现两笔一百二十。同金额里，编号一百零一排在一百零五前面。把金额换成升序，就可以查金额最小的订单。读题先划出主要排序字段和方向，再处理并列规则。多写一条规则，翻页和看排行榜都会更清楚。

### 00:12:17 用 LIMIT 和 OFFSET 取下一页

假设一页显示三笔。第一页看编号一百零一到一百零三。查询第二页时，仍然先按唯一编号排序，让两次查询采用同一顺序。LIMIT 三规定最多返回三行。OFFSET 三表示先跳过前三行，再从第四个位置开始接着取。把整张查询结果想成一个有顺序的清单，OFFSET 指定从哪里开始，LIMIT 指定取多少。

这一页输出一百零四、一百零五和一百零六。再下一页时，先跳过六行，得到最后两笔。实际写分页时，可以用一号页什么都不跳、二号页跳三行、三号页跳六行这样的计算。先固定排序，再决定每页大小。观察最后一页通常比前三行少，这组数据正好可以用来练习分页的尾部。

### 00:13:12 用 DISTINCT 去掉重复项

四位客户里有两位住在杭州。现在要整理发货城市名单，每个城市显示一次。在 SELECT 后加 DISTINCT，把相同的结果行留一份。这一页只选 city，所以两个杭州是相同的一行。上海、南京和杭州都还在，原来的两条客户记录也仍然保留。

本例最后按城市文字排序。先用三行结果确认城市名单，再想一个变形。如果查询同时选择 city 和 name，去重比较的是整个二元组合。杭州小林与杭州小陈是两种组合，会各出现一行。查有哪些不同城市时选一列，查有哪些城市和姓名组合时选两列，先确定你希望什么样的行相同。

### 00:14:06 用 LIKE 查找名称开头

现在从客户表查名字。运营想先筛出所有名字以小字开头的人。用 LIKE 写一个匹配模式。单引号里先写小字，后面接百分号，表示其后可以接零个、一个或更多字符。读模式时先找到固定部分，再读占位符。把百分号放前面，就变成按结尾匹配。

数据里小林、小周、小陈、小吴都符合，结果回到四行。试把百分号换成一个下划线，模式就专门找小字加一个字符。再想一个练习，如果想让名字中间任意位置包含林字，可以在林前后都放百分号。有业务样例时，挑一个应该匹配和一个应该排除的名字一起执行，看看模式是否把它们分开。

### 00:14:59 用 CASE 生成金额标签

报表可以对每笔订单加一个标签。我们先显示编号和金额，再在第三列显示大额或普通。CASE 里面用 WHEN 写条件。满足金额至少一百二十就取 THEN 后的大额，其他行使用 ELSE 后的普通。END 收住这个表达式，随后起名 tag。这个判断对进入结果的每一行分别计算。

按编号取前四行，金额是一百二十、八十、六十和二百。因此第一行和第四行显示大额，中间两行显示普通。若要加一个更高的金额等级，可以再写一条 WHEN，把高门槛排在前面。数据库按书写顺序试条件，命中后就取对应的结果。先写范围最窄的规则，标签会更符合预期。

### 00:15:55 练习 · 给第二名加上明确的并列规则

请预测第二名的订单编号。表里有两个一百二十元，还有更大的金额。先保留不超过一百二十的订单。剩下的按金额降序。同金额时，拿编号更大的排在前面。最后取前两行。给自己几秒钟，先圈出可能入选的两行，再确定它们的顺序。

二百和一百六十超过上限，被过滤掉。接下来最高的两笔，都是一百二十元。这里编号也写了 DESC，编号一百零五在一百零一前面。所以第一行是一百零五，第二行是一百零一。只写金额排序时，这两笔并列，题目没有规定它们之间的先后。日常做分页时也要加这种明确的并列规则。

## 00:16:47 聚合统计与分组

### 00:16:47 用 COUNT 和 SUM 看经营总览

老板先问，成功收款共多少笔，合计多少元。先从订单表保留已支付的记录。把五笔留下来的金额写在心里，一百二十、八十、二百、一百六十和九十。COUNT 星号数这些行一共有多少。SUM 把金额列里的值加起来。两项都把多行变成一个数字，属于聚合函数。

实际结果是五笔，合计六百五十元。输出只有一行，因为这一页把符合条件的记录当作整体汇总。可以先运行一条明细查询，逐笔核对筛选，再换成统计函数，这样有疑问时容易定位。如果关心所有销售状态，就调换或去掉状态条件。每种统计口径都可以用一段明确的过滤条件表达。

### 00:17:39 COUNT 星号与 COUNT 列

这张订单表一共有八行。现在想比较总订单数和带优惠码的订单数。COUNT 星号把每条记录数一次。COUNT 后放 coupon 这一列，只统计优惠码有值的那些行。表里只有一百零一和一百零四有优惠码，其他都是空值。两种计数会放在同一行，方便直接比较。

第一列显示八，第二列显示二。换成 COUNT amount，由于每笔都填写了金额，就会得到八。做统计时，把函数括号里的列名和业务目的连起来看。比如数已填写电话的人，统计电话这一列正好合适。要数名单里的全部人，就用 COUNT 星号。以后做左连接统计时，这个区别还会出现。

### 00:18:31 用 GROUP BY 按状态汇总

现在把全部订单按状态放进三个篮子，一篮已支付，一篮待支付，一篮已取消。GROUP BY status 就按状态分组。每种不同状态会得到一组。分好以后，不同组各自统计。你可以把这个过程理解成在纸上先画三栏，把每个订单记进自己的栏目。

对每一组计算笔数和金额合计，屏幕上每组一行。已支付五笔、六百五十，待支付两笔、一百五十，已取消一笔、一百二十。然后按状态文字排列。写分组查询时，SELECT 里放分组字段或根据组计算的值。用这种写法，每一列都能解释成这张统计表上的一项。

### 00:19:21 用 HAVING 过滤汇总结果

现在找已支付金额达到两百的客户。先从订单表选已支付的记录，待支付和取消的都留在统计范围外。然后按客户编号分组，把同一位客户的订单放进同一组。每组算出订单金额之和。此时客户一号是二百一十，二号是八十，三号是三百六十。

HAVING 在分组之后检查总额。二号没有达到二百，所以结果只剩一号和三号。按总额从大到小排列，三号排第一，一号排第二。判断该用 WHERE 还是 HAVING 时，先问条件看的是一笔原始订单，还是一组计算出来的数字。看订单状态用 WHERE，看客户累计金额用 HAVING。

### 00:20:12 平均值、最小值与最大值

继续看已支付的五笔。老板除了关心总额，还常问普通一单是多少钱，最小单和最大单分别是多少。AVG 会按有效的金额值求平均。本页把它包在 ROUND 里面，小数保留到两位。写这种表达式时，先读最里面的计算，再读外面要求的展示精度。

五笔总金额六百五十，平均是一百三十。MIN 找最小的八十，MAX 找最大的二百。屏幕上三项一起出现，可以顺手看出平均值位于最小和最大之间。自己验证的时候可以先挑两笔订单，用手算平均再对照执行。选的记录少一些，发现筛选或计算错误会更快。

### 00:21:00 练习 · 各客户有几笔已支付订单

请找出有至少两笔已支付订单的客户。先划出已支付的五笔，可以在纸上写它们的客户编号。把相同编号放一组，计算组内的行数。组内有两行及以上才保留。给自己几秒钟，先写出客户编号和对应笔数，然后按照编号顺序排好。

已支付的行按订单编号是第一、第二、第四、第六、第七笔。对应客户编号是一、二、三、三、一。一号出现两次，二号一次，三号两次。按门槛保留一号和三号。最后结果是编号一、两笔，以及编号三、两笔。原始行、分组结果、筛完的结果，这三层分别写下来，复杂一点也容易检查。

状态为待支付的有一百零三和一百零八两笔，原优惠码都是空。执行后查询这两笔，都显示待跟进。如果其中一笔已经填写信息，它会在空值检查这一步被排除。批量更新前可以运行同条件的 SELECT COUNT 星号，先记下预计影响多少行，再用相同规则复查结果。

### 00:44:21 练习 · 一条 UPDATE 选中哪一单

题目中两笔待支付订单，金额分别是六十和九十。请用两个条件逐行判断。更新目标的金额会加五，但后面的查询范围比更新宽。查询会列出所有待支付订单。你要写出两行结果，并在发生改变的那一行旁边画个圈。暂停几秒后一起核对。

一百零三号是待支付且金额六十，通过两个条件。一百零八号虽然待支付，金额九十超过门槛。只有一百零三号加五，变成六十五。查看时两行都会出现，依次为一百零三、六十五，以及一百零八、九十。调试时可以同时看一笔命中和一笔刚好没命中的记录，确认更新范围。

## 00:45:16 事务与索引

### 00:45:16 用 ROLLBACK 撤销练习修改

有时需要把多条操作作为一组处理。这一组叫事务。BEGIN 显式开始一次事务。在这套练习数据库里，编号一百零一的金额原来是一百二十。这里临时把它改成五十。如果同一个连接在回退前查询，就能看到自己刚做的修改。

接下来运行 ROLLBACK，把尚未提交的修改撤销。事务结束后，再查编号一百零一，金额回到一百二十。以后练习写入数据时，你可以先开启事务，执行修改和查询，验证反馈后再决定提交或回退。把执行过程分成这几个阶段，就能很清楚地知道什么时候只是试改，什么时候已经保存。

### 00:46:07 用 COMMIT 保存一组修改

练习数据里有两笔待支付订单，这次假设它们都补款成功。先开启事务，再按各自的编号修改状态。一开始已付款五笔，两次修改分别让一百零三和一百零八进入这个口径。此时可以在同一连接预览修改后的状态。

确认以后用 COMMIT 提交这一组修改，数据库结束事务并保存。再统计已支付订单，得到七笔。如果在提交前发现某个编号填错，就执行 ROLLBACK，再重新开始。真实程序通常在操作失败后先处理错误并按需要回退。这一页的两条更新都成功，因此可以一起提交。

### 00:46:53 用索引服务常见查找

如果订单很多，经常按客户编号找记录，就可以为这个字段建索引。把它想成书末的索引页，按一个键帮你定位可能的记录位置。CREATE INDEX 后给索引一个名字，再说明哪张表的哪一列。这个索引针对 orders 的 customer id。

创建完以后，查询写法照常。按一号客户筛选，再按订单编号输出一百零一、一百零三和一百零七。索引主要帮助数据库选择访问方式，结果依然由查询语句决定。维护索引需要存储空间，插入和修改时也要更新它。先找项目里经常执行的查询，再决定要为哪些列建立索引。

### 00:47:44 用查询计划看 SQLite 怎样找行

为了观察索引是否被选用，先建一个客户编号索引。接着把 EXPLAIN QUERY PLAN 放在现有查询前面。它返回数据库计划怎样访问数据。我们想知道这次会按客户编号查索引，还是扫描表中的行。通常先把这个命令用于经常执行、看起来慢的查询。

这一例的计划里能找到 SEARCH 和索引 idx customer，说明执行器选择通过索引定位记录。这里显示的是访问计划，下一次直接运行 SELECT 才会得到查询结果。换成真实项目，可以先记录旧计划，建索引后再看一次，并在有代表性的数据上测时间。数据分布和查询写法都会影响数据库的选择。

### 00:48:36 理解复合索引的列顺序

索引还可以同时包含两个字段。这里先写状态，再写日期，可以想成先把订单按状态放进不同分区，再在每个分区里按日期排列。查询如果先确定已支付，再取某个日期区间，这个排列方式就很适合查找。

本页先找已支付，再限制从七月开始。结果是七月一日、三日和四日三笔。最后按日期和编号排序。设计复合索引时，先把查询中最常用的条件写出来，观察是按哪个字段精确定位、再按哪个字段查范围。判断是否用上索引，仍然可以套上上一页的查询计划命令。

### 00:49:22 练习 · 回滚发生在查询前

题目先打开事务，再删除一百零五号。删除语句本身会命中订单表中那一条已取消记录。看清回滚和查询的先后顺序。暂停几秒，分别写下回滚前能不能查到这条记录，回滚后屏幕会显示什么。想想把第三行换成提交以后，答案会怎样变化。

删除以后，同一连接立刻查这笔订单会查不到。接着回滚，删除被撤销。所以最终查询仍然返回一百零五号，状态是已取消。若把回滚改成提交，删除就会保留下来，查询返回零行。做事务题时，把开始点、每项写入和结束点划在时间线上，很容易看清最后保存了什么。

## 00:50:18 窗口函数与综合报表

### 00:50:18 给每笔订单标上顺序号

先留已支付的五笔。现在想显示每笔金额，还希望附带从大到小的顺序号。ROW NUMBER 负责生成顺序号。OVER 的括号中写金额降序，同金额时按订单号升序。数据库依次给结果行编号，从一开始。和前面的分组汇总相比，每笔明细在这里都保留下来。

屏幕显示订单号、金额和名次。最先是两百那笔，接着一百六十，然后一百二十、九十、八十。最后的 ORDER BY 让输出按顺序号排列。窗口里的排序决定怎么计算编号，外层排序决定怎么展示结果。自己写时可以分别问，计算顺序是什么，呈现给读者的顺序又是什么。

### 00:51:11 用 PARTITION BY 给每位客户单独编号

改一个需求。现在想知道每位客户各自的最大订单。先保留已支付的明细，同时展示客户号、订单号和金额。给 ROW NUMBER 增加 PARTITION BY customer id。把记录按客户分成不同的分区，再在各区按金额从大到小排序。每个分区自己的编号都从一开始。

最终按客户号和各自的编号输出。客户一号先一百二十后九十。二号只有八十。三号先二百后一百六十。位置一在每个客户分区都会出现。如果改为按下单日期排序，位置一就表示这位客户时间最早的订单。分区回答谁和谁一起排，排序回答组里谁在前。

### 00:52:03 报表第一步 · 计算每位客户的付款汇总

从这里做一份可实际使用的付款报告。目标是每个客户一行，显示姓名、付款笔数、付款总额，包含零笔客户。客户表放在左边。只在 ON 中匹配已支付订单。每个客户一组。先数右表订单编号，再加总金额，方便一起检查这两个指标。

小林两笔，二百一十。小周一笔，八十。小陈两笔，三百六十。小吴没有匹配，COUNT 返回零，SUM 的空结果由 COALESCE 显示为零。最后按总金额降序，得到小陈、小林、小周、小吴。先把这一步的数字核对好，下一页再加总额排名。

### 00:52:51 报表第二步 · 在汇总结果上计算排名

把上一页的汇总装进 WITH。中间结果包含客户编号、姓名、总额，仍然每人一行。可以先执行括号里的查询，核对小吴为零。外层显示姓名和总额，再用 DENSE RANK 按总额降序编号。两个总额相同时，它们会拿到同一名次，下一个不同金额接下一名。

这四个人金额都不同，名次依次是一到四。最后按名次和客户编号显示，使并列时仍有可预测的展示顺序。这里名次只看金额。把客户编号也写入窗口排序的话，同额的人会被当成不同的排序键。做这类题，先定义并列规则，再决定用普通顺序号还是允许并列的名次。

### 00:53:43 读懂报表的几层计算

综合报表交付之前，再做一次总数校验。这里从同一份初始数据出发，先按客户统计已支付总额。这一步直接从订单表开始，因此只得到有付款的三位客户。中间三行是二百一十、八十和三百六十。外面统计三行的数量与总和。

结果得到三位有付款的客户，总金额六百五十元。把这个总额拿去对照直接从订单求和的结果，两边一致。做报表时很适合用这种独立口径来交叉核对。回看整条 SQL，可以说清内层一行是一位客户，外层只剩一行表示经营总览。先搞清每一层的一行是什么，再数返回行。

### 00:54:33 练习 · 每位客户最贵的一笔已支付订单

最后一道题。先取已支付的订单，按客户分区，再按金额从高到低编号。外层只留每区的位置一。给自己几秒钟，写下每位客户留下的订单号，再检查哪位客户没有出现在最终表里。可以从第四章用过的五笔已付款订单开始找。

客户一号的位置一是一百零一，金额一百二十。二号只有一百零二，金额八十。三号的位置一是一百零四，金额两百。最终三行。小吴在基础订单集中没有付款记录，因此没有分区。到这里，从表与行列、条件和排序，到分组、连接、写入、事务和窗口都用过一遍。课后可以改用六月作为时间条件，跑出一份新的客户报表。

### 00:55:32 延伸练习 · 只统计六月的付款

做完按客户排名，再把报告改成只看六月。业务要求仍然是每位客户一行，因此客户表继续放在左边。先找编号相等、而且已经付款的订单。接着把日期范围加进 ON。只匹配六月一日开始、七月一日之前的记录。这样没有六月付款的客户也能留下，符合报表的名单规则。

按客户分组后，小林一百二十，小周八十，小陈和小吴都是零。六月的那笔六十元处于待支付状态，因此月报只计算前两笔。按照总额降序，加编号作为并列规则。做完可以用一条简单查询，把只符合日期和状态的两笔订单拿出来相加，结果是两百。把项目查询和这个小验证写在不同文件里，之后修改报表还能重复核对。

### 00:56:30 延伸练习 · 用视图保存查询规则

如果经营总览和付款月报都经常使用已支付订单，可以考虑给这个查询固定一个名字。用 CREATE VIEW 建立视图 paid orders。定义里的 SELECT 说明它提供哪些列和哪些行。以后读这个名字，就能拿到当前已支付的订单明细。和本章前面学到的一次性 WITH 相比，这个视图定义会作为数据库里的对象保存下来。

建好视图以后，对它做计数和求和，结果是五笔、六百五十元。如果订单表里的状态以后改变，再查询这个普通视图就按新的数据计算。把经常用的筛选写成视图，可以让多个查询沿用同一口径。第一次使用视图时，先单独执行视图定义里的 SELECT，确认筛选的行和列，再给它起一个说明用途的名字。

### 00:57:25 回顾 · 把一个问题翻译成查询

最后用一句常见需求回顾，找出累计付款最多的客户。先问结果的一行应该代表什么。这里一行代表一个客户，需要客户编号和总额。原始数据来自订单表，原表一行是一笔订单。先只留已支付的订单，再按客户编号分组。这样每组的金额合计才是这个客户的累计付款。

汇总后从大到小排，金额一样就按客户编号，取第一行。最后查到三号，三百六十元。需要姓名时，可以再把它和客户表按编号连上。课后从工程里的初始化脚本开始，把基础查询、六月报表和回滚练习各跑一遍，再换一个门槛或月份。每次先预测行数和关键结果，执行以后再核对。这套习惯会比背下所有关键词更有用。
